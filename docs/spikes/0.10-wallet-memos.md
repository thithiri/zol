# Spike 0.10: wallets, binary memos and ZIP 321 links

Date: 2026-10-10. Status: research only. Every finding below comes from reading source code, ZIPs and issues. No wallet was run. Commits are pinned, and line numbers refer to those commits.

## Question

The design's deposit (design-v0.3, "Deposit") is a ZIP 321 link: `zcash:<vault UA>?amount=X&memo=<base64url>`. The memo is a 512-byte binary blob whose first byte is `0xFF`, so it is not UTF-8. The spike asks three things of each target wallet:

1. Does it parse the link, and does it send the memo bytes unmodified, change them, or reject them?
2. Can it make the shielded send the design needs?
3. Does a link carrying that memo still fit in a scannable QR code?

## Headline

1. **No wallet currently delivers a binary `0xFF` memo reliably from a ZIP 321 link.**
   - The reference parser in librustzcash handles the memo correctly.
   - Most wallet apps then discard it or convert it to text. Several drop the memo silently but still send the funds, which is the worst outcome for ZOL.
2. **The "Orchard send" the design assumes no longer exists.**
   - NU6.3 ("Ironwood") activated on mainnet at height 3,428,143 (2026-07-28) and on testnet at 4,134,000. Testnet is now past 4.46M.
   - From activation, no value may enter the Orchard pool, and Orchard actions cannot transfer between addresses.
   - New shielded value goes to the **Ironwood pool**, in v6 transactions. Addresses are unchanged: Orchard-protocol receivers receive Ironwood notes.
   - Details are in the Ironwood section below. This affects the whole design, not just wallets.

## 1. Reference parser: librustzcash `zip321`

Source: zcash/librustzcash @ `3c76c2d822446a68b67cd25692aaf92b4f6cb98c`. The crate is 0.10.0-pre.1; the latest release is 0.9.0 (2026-08-18).

**Decoding.**
- `memo_from_base64` runs `BASE64_URL_SAFE_NO_PAD.decode(s)` and then `MemoBytes::from_bytes` ([components/zip321/src/lib.rs L149-157](https://github.com/zcash/librustzcash/blob/3c76c2d822446a68b67cd25692aaf92b4f6cb98c/components/zip321/src/lib.rs#L149-L157)). I checked this myself.
- Padding (`=`) is rejected. `=` is not a qchar either. Non-canonical trailing bits are rejected.
- The value is not percent-decoded (L837-840).

**Length.**
- `MemoBytes::from_bytes` rejects more than 512 bytes (`TooLong`) and zero-pads shorter input to 512 ([components/zcash_protocol/src/memo.rs L103-111](https://github.com/zcash/librustzcash/blob/3c76c2d822446a68b67cd25692aaf92b4f6cb98c/components/zcash_protocol/src/memo.rs#L103-L111)). I checked this myself.
- **Nothing checks UTF-8 or the first byte, so a `0xFF` binary memo parses cleanly.**

**Classification.** `Memo::try_from(&MemoBytes)` ([memo.rs L211-226](https://github.com/zcash/librustzcash/blob/3c76c2d822446a68b67cd25692aaf92b4f6cb98c/components/zcash_protocol/src/memo.rs#L211-L226), checked myself):

| First byte | Result |
|---|---|
| `0xFF` | `Memo::Arbitrary([u8; 511])` |
| `≤0xF4` | `Text`; must be valid UTF-8 |
| `0xF6` followed by all zeros | `Empty` |
| anything else | `Future` |

**Rendering.** `memo_to_base64` encodes `memo.as_slice()`, which strips trailing zero bytes (memo.rs L123-134). A canonical URI therefore omits the zero padding, and receivers pad it back to 512.

**Transparent recipients.** A memo on a transparent, TEX or transparent-only UA recipient is rejected with `TransparentMemo` (lib.rs L198-216 and L690-698). A UA with an Orchard-protocol or Sapling receiver can take a memo.

**What ZIP 321 says.**
- Memos are unpadded base64url, at most 512 bytes after decoding ([zip-0321 L313-319](https://github.com/zcash/zips/blob/3af03aa3ad991874d86b8cf35919bc9b4671e8ba/zip-0321.rst#L313-L319)).
- **It sets no limit on URI or QR length.**
- It warns that clients "may not support the memo parameter" (L440-449).

## 3. URI and QR size

QR codes must use byte mode: base64url is case-sensitive and the `zcash:` scheme is matched case-sensitively, so alphanumeric mode is not possible. UA lengths are 106 characters for an Orchard-only receiver on mainnet (110 for `utest1…`), 178 with Sapling, and 213 with Sapling and transparent. The table assumes `amount=0.12345678`.

| URI | Characters | QR version at ECC L / M / Q / H |
|---|---|---|
| Orchard-only UA, full 512-byte memo (683 base64url characters) | 819 | v20 / **v23 (109×109)** / v28 / v32 |
| Three-receiver UA, full 512-byte memo | 926 | v21 / v25 / v30 / v34 |
| Orchard-only UA, 0xFF plus 183 field bytes with trailing zeros stripped | 382 | v13 / **v15 (77×77)** / v18 / v20 |

- Version 23 at ECC M scans on-screen at close range with a current phone. It is marginal in print or on low-DPI screens. This is general practice, not something I measured.
- Removing trailing zero bytes before encoding loses nothing, because receivers pad back to 512, and matches librustzcash's canonical form. It roughly halves the QR size for a memo with no app data. It is also what keeps Zodl Android on its byte-exact path.

## 4. Ironwood (NU6.3): the deposit is no longer an "Orchard send"

Sources:
- [ZIP 258 L66-104](https://github.com/zcash/zips/blob/3af03aa3ad991874d86b8cf35919bc9b4671e8ba/zips/zip-0258.md#L66-L104) (Draft): activation heights and consensus rules. Checked myself.
- Zebra 6.4.2 `zebra-consensus/src/transaction/check.rs` L199-255: `orchard_value_balance_non_negative` and `coinbase_orchard_component_empty`.
- [ZIP 326](https://github.com/zcash/zips/blob/3af03aa3ad991874d86b8cf35919bc9b4671e8ba/zips/zip-0326.md) L119-120 and L306-316: wallet rules and receiving.
- The coordinator independently confirmed the activation heights from zcash_protocol 0.10.6 and orchard 0.15.5.

**What changed.** For every block at or above the NU6.3 height:
- `valueBalanceOrchard` must be ≥ 0, so nothing can enter the Orchard pool.
- Orchard-pool actions must have `enableCrossAddress = 0`.
- Coinbase may not create Orchard notes.
- New shielded value goes into the Ironwood pool through v6 transactions.

**Addresses.**
- There is **no separate "Ironwood address"**. Receivers belong to the Orchard *protocol*, so an existing Orchard receiver or UA receives Ironwood notes (ZIP 326 L306-316).
- ZIP 321 and UA handling are unchanged.
- There is still no standalone raw Orchard address encoding. Use a UA containing only the Orchard receiver (106 characters).

**Wallets.** ZIP 326 says a wallet MUST NOT send to an external receiver in the Orchard pool after NU6.3; librustzcash routes such payments to `PoolType::IRONWOOD` (`input_selection.rs` L966-995). Per wallet:

| Ironwood support | Wallets |
|---|---|
| Send and receive | Zodl iOS and Android, Zkool, Zingo, Cake, Edge, Unstoppable, Zallet; Brave on desktop only |
| None | YWallet, Nighthawk, Zecwallet Lite |

**Memo.** Still 512 bytes per note. Memo bundles (ZIP 231) are a draft for v7 transactions and are not part of NU6.3.

## Conclusions and implications for design-v0.3

1. **Restate the deposit and the vault in Ironwood terms. This is a blocking design change, outside this spike's scope.**
   - "The player approves one shielded Orchard send" becomes "one shielded send to the vault's Orchard-protocol receiver, landing in the Ironwood pool (v6 transaction)".
   - The vault's head-note chain, payouts, refunds, the scanner (decrypting Ironwood bundles), the `pczt` pipeline (Phase 0.3-0.6), FROST spend-authorization (0.7) and the per-app key tweak (0.8) all need checking against Ironwood and v6.
   - ZIP 326's `use_qsk` (ZIP 2005 quantum recoverability) changes how `rivk`/`ovk` are derived, which touches the per-app `nk`/`rivk` derivation in 0.8.
   - The memo's 43-byte raw payout receiver is still valid: an Orchard-protocol receiver.
2. **The binary `0xFF` memo should not be the only deposit format.** Recommended changes for v0.3.1:
   - **A text-safe primary memo.** Use ASCII `ZOL1:` followed by base64url(payload), at most 511 bytes (Zingo's limit).
     - That leaves room for a binary payload of at most 379 bytes. The v2 fields are 183 bytes, so app data drops from 329 to about 196 bytes.
     - It must not start with `0x`, because Zingo hex-decodes those, and must have no trailing NULs, because the Swift SDK rejects them.
     - Text survives Zodl iOS and Android, Zingo, Zkool's single-payment path and Edge.
   - **Scanner and attestor accept every form a memo can arrive in:**
     - the `0xFF` binary memo;
     - `ZOL1:` text;
     - text that is base64url of either, which is what Unstoppable iOS produces when the parameter is 512 characters or fewer.
     - The session signature covers the decoded payload, so the encoding is not security-relevant.
   - **Strip trailing zeros** in the link.
   - **Treat a missing memo as a normal case.** Zodl iOS, Cake, Unstoppable Android and Zkool's single-payment path send the funds without a memo. Today such a deposit stays `Seen` forever, because the design holds it "until the sender proves the payment", and no proof procedure is specified. The strongest fix is a **fresh diversified receiver per deposit**: the page asks the gateway for a diversified address bound to the session key, so the receiver identifies the deposit even when the memo is lost. The design already scans every diversified address. Otherwise specify the claim procedure.
3. **The QR code is the main path, not deep links.** Zodl and Zkool ignore `zcash:` deep links. The page should show the QR plus copyable address, amount and memo text, and name the tested wallets.
4. **Phase 5 E2E needs a real wallet matrix.** At minimum Zodl iOS, Zodl Android, Zingo and Zkool on testnet, because everything above was read from source and none of it was run.

Unverified:
- The Zodl Android threshold comes from Python's UTF-8 replacement rules, not the JVM's.
- Zkool's multi-payment path and the Unstoppable SDK forks were read in source only.
- The QR scannability limits are rules of thumb.
