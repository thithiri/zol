# Spike 0.7: rerandomized FROST over Pallas (ZIP 312)

**Result: PASS.** The 0.3 payout's spend authorization was produced by 2-of-3 FROST (`reddsa::frost::redpallas`), once with a trusted dealer and once with a DKG, in both the Orchard (v5) and Ironwood (v6) pools.

- The FROST group key is the Orchard `ak`. The vault FVK is `(ak, nk, rivk)`.
- The PCZT's `alpha` is the randomizer.
- The aggregate signature was inserted with `Signer::apply_orchard_signature` / `apply_ironwood_signature`, which verifies it under `rk`.
- The extracted transaction verifies fully offline.

## Recommendations

1. **Use reddsa 0.5.2 with the `frost` feature**, which pulls in frost-rerandomized 3.0.0 and frost-core 3.0.0. Pin `frost-rerandomized = "=3.0.0"` directly as well, because ZOL needs `Randomizer::from_scalar`.
2. **Accept that the randomizer is chosen by the coordinator, not derived from the round-1 commitments.**
   - Why: the orchard builder picks `alpha` and commits `rk = ak + [alpha]G` into the effects before any FROST round. frost-rerandomized 3.0's recommended `RandomizedParams::new_from_commitments` / `sign_with_randomizer_seed` derive the randomizer from the round-1 commitments, so they cannot be used.
   - What we used instead: the deprecated `frost_rerandomized::sign(.., Randomizer::from_scalar(alpha))` and `RandomizedParams::from_randomizer`. Its docs say: "not recommended … unless for compatibility reasons with specifications on how the randomizer must be generated". This matches ZIP 312's model, where the coordinator generates the randomizer and sends it confidentially.
   - **External review item:** whether coordinator-chosen `alpha` weakens anything beyond unlinkability. The upstream change was a hedge against a coordinator's bad RNG.
   - A future option is to seed the builder's RNG from the round-1 commitments. This is not supported, because the builder draws `alpha` internally.
3. **The sign rule is handled by reddsa; do not add your own negation at keygen.**
   - `post_generate`, used by `generate_with_dealer` and `split`, and `post_dkg`, used by `dkg::part3`, both call `into_even_y`.
   - If the group key has ỹ = 1, it negates the group key, every signing share, every verifying share and, for dealer shares, the VSS commitments.
   - This is sound because negation is linear: Σλᵢ(−sᵢ) = −s.
   - It matches what orchard does for a single key: `SpendAuthorizingKey::from` negates `ask` when ỹ(ak) = 1.
4. **The signer checks the sighash itself** (0.6, item 12) and signs one FROST signature per real spend, each with that action's `alpha`.

## What was tested

`spikes/zcash/tests/spike_0_7_frost_pallas.rs` and `src/frost_vault.rs`:

**`sign_rule_even_y`**

- An `ak` with ỹ = 0 gives a valid FVK. Its negation, with ỹ = 1, is rejected by `FullViewingKey::from_bytes`, so Orchard needs ỹ(ak) = 0.
- Trusted dealer: 32 out of 32 group keys come out with ỹ = 0.
- `keys::split` of 32 random keys: 13 to 16 per run had ỹ = 1. For each of these, the output group key is the input key negated.
- DKG: 8 out of 8 group keys come out with ỹ = 0.

**`threshold_subsets`**

- DKG 2-of-3. Every pair {1,2}, {1,3} and {2,3} produces a RedPallas signature that orchard's `VerificationKey<SpendAuth>` accepts under `ak + [alpha]G`.
- One signer fails: `IncorrectNumberOfCommitments`.

**`frost_dealer_payout` and `frost_dkg_payout`** (each in both pools)

1. Take `ak` from `pubkeys.verifying_key()` and check ỹ = 0.
2. Pick random `nk` and `rivk` (canonical, via `from_uniform_bytes`) and build `vault_fvk = FullViewingKey::from_bytes(ak || nk || rivk)`.
3. Receive the head note at the vault address and build the 0.3 payout.
4. Run IoFinalizer, then the Prover.
5. Compute `sighash = Signer::new(..).shielded_sighash()`.
6. Read `alpha` from the PCZT through the Verifier role, and run `checks::check_real_spend`.
7. Run FROST round 1 (`round1::commit`) and round 2 (`frost_rerandomized::sign` with `Randomizer::from_scalar(alpha)`) for signers {1,3}.
8. Run `rerandomized::aggregate` with `RandomizedParams::from_randomizer(group_vk, alpha)`, and verify the result under the randomized key.
9. Serialize the signature (`R || S`, 64 bytes, the same encoding as a RedPallas signature) and pass it to `apply_*_signature`. The pczt Signer verifies it under `rk`.
10. Run SpendFinalizer and TxExtractor, then `verify::verify_raw` (proof, spend-auth signature, binding signature, sighash recompute).
11. The recipient decrypts the payout, and the vault's internal IVK decrypts the new head.

Output of one run:

## Orchard's ak sign rule and reddsa

- **Orchard** (`orchard/src/keys.rs`): `SpendValidatingKey::to_bytes` asserts `b[31] & 0x80 == 0`, and `from_bytes` rejects ỹ = 1. Spend keys are generated by negating `ask` when needed.
- **reddsa 0.5.2** (`src/frost/redpallas.rs`): has a `keys::EvenY` trait (`has_even_y`, `into_even_y`) implemented for `PublicKeyPackage`, `SecretShare` and `KeyPackage`. `PallasBlake2b512::post_generate` and `post_dkg` apply it automatically.
- Signing does no even-Y processing (there is no `pre_sign` override). This is correct, because `rk = ak + [alpha]G` has no sign rule.
- **Note:** I did not check whether the Action circuit itself constrains ỹ(ak). The libraries enforce the rule at the encoding level: FVK, UFVK and `SpendValidatingKey`.

## Exact versions

reddsa 0.5.2 (`frost`), frost-rerandomized 3.0.0, frost-core 3.0.0, orchard 0.15.5, pczt 0.9.3, zcash_primitives 0.30.1, pasta_curves 0.5.2. The pin is required: orchard 0.16 and reddsa 0.6 dropped FROST.

## Implications for design v0.3

- The "Vault spend key: Pallas, rerandomized FROST (ZIP 312)" row is confirmed workable with the real pczt flow.
- State the randomizer model: the Constructor picks `alpha`, it travels in the PCZT, and the PCZT must therefore go to signers over a confidential channel. This is already in the design ("the re-randomizer, which ZIP 312 requires to travel over a confidential channel"). Add that the hedged randomizer derivation in frost-rerandomized 3.x is incompatible with pczt, and list that as a review item.
- One FROST session per real spend: a payout spending the head plus k deposit notes needs k+1 signatures. Round 1 can be batched.
- Plan 4.5 ("any signer can aggregate"): `aggregate` needs only the public key package, the `SigningPackage`, the shares and `alpha`. Any signer that knows `alpha` can aggregate.
