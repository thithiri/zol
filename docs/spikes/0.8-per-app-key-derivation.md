# Spike 0.8: per-app vault key derivation (spec for external review)

**Result: PASS, with one design correction.**

**What works.** One FROST key generation yields an Orchard (or Ironwood) spend key and a full viewing key for every app:

- the spend key through a public additive tweak applied to every share;
- the viewing key through a PRF of a master viewing secret.

The spike signed a real payout from app A's vault with 2-of-3 FROST under the tweaked shares, and it verifies. App A's viewing key cannot decrypt app B's notes in either scope.

**The correction.** The tweak isolates *viewing* but not *signing*. FROST signatures under different apps' keys are interchangeable by shifting the randomizer. The spike demonstrated this end to end: app A's tweaked shares authorized a valid transaction spending app B's head. The only thing that stops it is the signer's nullifier check against its own note set. The design must state that check as the cross-app isolation mechanism (section 5.2).

---

## 1. Scope and status

This section is offered for external review. ZIP 312 covers splitting `ask` and rerandomized signing. It does not cover key generation, deriving several spend keys from one group key, or the other viewing-key components (`nk`, `rivk`). Everything below is ZOL's own construction.

## 2. Notation

| Symbol | Meaning |
|---|---|
| `G` | Orchard spend-authorization base point `G^Orchard` (reddsa `orchard::SpendAuth::basepoint()`, also FROST(Pallas, BLAKE2b-512)'s generator) |
| `q`, `p` | Pallas scalar field order, base field order |
| `repr_P(P)` | 32-byte Pallas point encoding: x-coordinate little-endian, with the top bit set to ỹ (the y sign bit) |
| `ỹ(P)` | the top bit of `repr_P(P)` |
| `LEOS2IP`, `I2LEOSP_n` | as in the Zcash protocol spec |
| `ToScalar(x)`, `ToBase(x)` | `LEOS2IP_512(x) mod q` and `mod p` (`pallas::{Scalar,Base}::from_uniform_bytes`), exactly as Orchard uses `PRF^expand` outputs |
| `H(pers, m)` | BLAKE2b-512 with 16-byte personalization `pers` |
| `n`, `θ` | number of signers (3) and threshold (2) |
| `s`, `sᵢ`, `Yᵢ = [sᵢ]G` | group secret (never materialized), signer i's FROST signing share, verifying share |
| `ak_group = [s]G` | FROST group verification key, after reddsa's even-Y normalization |
| `K` | 32-byte master viewing secret, held by every operator |
| `app_id` | the app's 32-byte Solana program ID |

## 3. Derivation

### 3.1 Inputs

- `ak_group`: the 32-byte `repr_P` of the FROST group key output by the DKG.
  - reddsa's `post_dkg` has already negated the key and all shares if ỹ was 1.
  - All signers must use these exact bytes.
  - Keep `ak_group` non-public (section 5.4).
- `K`: generated once, uniformly at random. It is not threshold-shared, so any one operator can view every app.
- `app_id`.

### 3.2 Counter search

For `c = 0, 1, 2, …` (a u32), take the first `c` that passes every check:

```
t_c      = ToScalar( H("ZOL_app_ak_tweak", ak_group ‖ I2LEOSP_16(len(app_id)) ‖ app_id ‖ I2LEOSP_32(c)) )
A_c      = ak_group + [t_c] G                       (as points)
reject c if A_c = 𝒪  or  ỹ(A_c) = 1

nk_c     = ToBase  ( H("ZOL_app_view_key", K ‖ 0x00 ‖ I2LEOSP_16(len(app_id)) ‖ app_id ‖ I2LEOSP_32(c)) )
rivk_c   = ToScalar( H("ZOL_app_view_key", K ‖ 0x01 ‖ I2LEOSP_16(len(app_id)) ‖ app_id ‖ I2LEOSP_32(c)) )
reject c if FullViewingKey::from_bytes(repr_P(A_c) ‖ I2LEOSP_256(nk_c) ‖ I2LEOSP_256(rivk_c)) fails
            (i.e. ivk = 0 or ⊥ in either scope; probability ≈ 2^-250)
```

Then:

```
c_app, t_app = c, t_c
ak_app       = A_c
fvk_app      = (ak_app, nk_c, rivk_c)
```

The rest is standard Orchard: `dk`, `ovk`, the internal FVK, `ivk` and all diversified addresses follow from `fvk_app`.

The accepted counter is a deterministic public function of `ak_group` and `app_id`. Store `c_app` with the app, and recompute it to check.

### 3.3 Spend shares

The signer holding `(i, sᵢ, Yᵢ)` for the group derives app shares on the fly:

```
sᵢ,app = sᵢ + t_app            (mod q)        — every signer adds the full t_app
Yᵢ,app = Yᵢ + [t_app] G
Y_app  = ak_group + [t_app] G = ak_app
```

**Correctness.** For any signing set `S` with `|S| ≥ θ`, the Lagrange coefficients at 0 satisfy `Σ_{i∈S} λᵢ = 1`, so:

```
Σ_{i∈S} λᵢ sᵢ,app = s + t_app·Σλᵢ = s + t_app
```

Equivalently, the shared polynomial `f(x)` becomes `f(x) + t_app`: only the constant term changes. The spike checks that adding `t/n` to each share instead makes aggregation fail with `InvalidSignatureShare`.

**Usage.** Store only the base shares. Derive app key packages per signing session. FROST refresh and repair of the base shares commute with the tweak.

### 3.4 Signing

Signing a real spend of app X's note uses rerandomized FROST (spike 0.7) on `(sᵢ,X, Yᵢ,X, ak_X)` with the action's `alpha`. The signature verifies under `rk = ak_X + [alpha]G`.

## 4. The sign rule

Orchard requires ỹ(ak) = 0: `SpendValidatingKey::from_bytes` and `FullViewingKey::from_bytes` reject ỹ = 1. A randomized `rk` has no sign rule. There are two sound ways to meet the rule for `ak_app`.

**(a) Counter retry. Chosen.** Skip any `c` with ỹ(A_c) = 1.

- **Soundness:** `t_c` is public and the only thing revealed is ỹ, which is public anyway. Shares keep the plain relation `sᵢ,app = sᵢ + t_app`.
- **Cost:** expected 2 hash evaluations and point additions. Spike histogram for the accepted `c` over 256 random app ids: `[134, 62, 31, 12, 9, 2, 4, 2]` for c = 0, 1, 2, 3, 4, 5, 6, ≥7. That is geometric(½), as expected.

**(b) Negate the whole tweaked key.**

```
ak_app = −(ak_group + [t]G)
sᵢ,app = −(sᵢ + t)
Yᵢ,app = −(Yᵢ + [t]G)
```

- **Soundness:** this is also sound for FROST, because negation is linear: `Σλᵢ(−(sᵢ+t)) = −(s+t)`. reddsa's own `EvenY::into_even_y` does exactly this for the group key. The spike signed 2-of-3 under a negated tweaked key and verified the result.
- **Why not chosen:** it makes the app key a sign-dependent function, `±(s + t)`, which every implementation must reproduce identically. It also composes awkwardly with reddsa's own even-Y step on the base key.

Option (a) keeps one formula. **Recommendation: (a).**

## 5. Security notes for the reviewer

1. **Key isolation: none, by design.** `t_app` is public. Anyone holding `s` holds `s + t_app` for every app, so a threshold of signers controls every app's vault. This matches the design's "accounting isolation, not key isolation".
2. **Signing isolation: none at the signature layer. This is the correction.** For any apps A and B, any message `m` and any randomizer `α`:

   ```
   ak_B + [α]G = ak_A + [α + t_B − t_A]G
   ```

   A FROST session run with app A's shares and randomizer `α' = α + t_B − t_A` therefore outputs a valid spend authorization for app B's note. Shares differ by the public constant `t_A − t_B`, so the FROST transcripts are identical too.

   The spike demonstrated this in full:
   1. Build and prove app B's payout.
   2. Replace the PCZT `alpha` field with `α'`. `alpha` is not an effect, so the sighash does not change.
   3. App A's gateway `rk` test passes: `rk == ak_A + [α']G`.
   4. 2-of-3 signing with app A's tweaked shares produces a signature that the pczt Signer accepts.
   5. The extracted transaction spending **app B's head** verifies fully.

   The only check that stopped it was the nullifier test: the spent note's nullifier must be `note.nullifier(fvk_A)` for a note in app A's own scan, and app B's nullifier is computed with `nk_B`.

   **Requirement:** a signer authorizes action `j` for app X only if `rk_j = ak_X + [α_j]G` **and** `nf_j` equals the nullifier, under `fvk_X`, of a spendable note of app X in its own scan. The cross-app question applies to every spend a signer authorizes, not only the head.
3. **Viewing isolation.** `nk_app` and `rivk_app` are outputs of a keyed PRF (BLAKE2b keyed by `K` through the input) on distinct, injectively encoded inputs. Under the PRF assumption they are independent across apps, so `fvk_A` reveals nothing about `nk_B` or `rivk_B`. The spike confirms that app A's IVKs (both scopes) cannot decrypt notes sent to app B's external or internal address, and that `fvk_A.scope_for_address(addr_B) = None`.
4. **Linking ak values.** Because `t_app` hashes `ak_group`, someone who sees `fvk_A` (which contains `ak_A`) but not `ak_group` cannot compute `ak_group` or any `ak_B`: `t_A` needs `ak_group`. So keep `ak_group` private to the operators. Even if `ak_group` leaks, `ak_B` alone does not let anyone find app B's addresses or notes (that needs `nk_B` and `rivk_B`), and spends stay unlinkable through the secret `α`.
5. **Related-key attacks.** The additive tweak is the same kind of shift as the rerandomizer `α`. RedPallas hashes `rk` into the challenge (key-prefixing), so the additive related-key forgeries known for un-prefixed Schnorr do not apply. The security argument should be the same one used for rerandomized FROST, with one extra fixed public shift. **Reviewer item:** confirm this composition, and confirm the reliance on a coordinator-chosen `α` (spike 0.7).
6. **Domain separation.**
   - The two personalizations `ZOL_app_ak_tweak` and `ZOL_app_view_key` are 16 bytes each and distinct from Zcash's (`Zcash_ExpandSeed`, `Zcash_RedPallasH`, …) and FROST's (`FROST_RedPallas*`).
   - The tag byte 0x00 or 0x01 separates `nk` from `rivk`.
   - A length prefix makes `app_id` encoding injective.
   - The counter is fixed-width.
   - Consider adding a network id and a version byte before mainnet, so testnet and mainnet keys from the same `K` cannot collide.
7. **Reduction bias.** Reducing 512 bits mod `q` or `p` has negligible bias, the same as Orchard's own `ToScalar` and `ToBase`.
8. **Even-Y of the base key.** It is not needed for app keys, but reddsa normalizes it anyway. All parties must use the post-normalization `ak_group`.

## 7. What was tested

`spikes/zcash/tests/spike_0_8_per_app_keys.rs`, using `src/perapp.rs` and `src/frost_vault.rs`:

**`derivation_properties`**

- Run a 2-of-3 DKG.
- Derive keys for 256 random app ids. Every one has ỹ(ak) = 0 and a valid FVK. The only retries were for the sign rule.
- Tweak the key packages for app A and check:
  - `Y_app == ak_app`;
  - `[sᵢ,app]G == Yᵢ,app` for every share;
  - every 2-subset signs under `ak_app + [α]G`.
- Shifting shares by `t/3` instead fails.
- The negation alternative signs correctly.

**`per_app_payout_and_isolation`** (Ironwood, v6)

- Viewing isolation in both scopes, as in 5.3.
- App A's payout, signed by 2-of-3 FROST under the tweaked shares, extracts and fully verifies.
- App B's shares do not produce a valid signature for app A.
- The cross-app relabelling attack (5.2) succeeds when unchecked and is caught by `check_real_spend`.

**`test_vectors`**: section 6.

## 9. Implications for design v0.3

- **Keys section.** "Each app's spend key is the group key plus a public per-app tweak added to every signer's share; the viewing components are derived per app from a master secret" is confirmed, with the exact construction above. Add:
  - the counter rule for the sign rule;
  - that the tweak hashes `ak_group`, and that `ak_group` stays private;
  - that `K` is a single non-threshold secret, so one operator sees every app.
- **Real-spend rule.** "A spend whose verification key follows from the vault key and the supplied re-randomizer is a real spend" is **not sufficient on its own**: the `rk` test passes for another app's spend under a shifted `alpha`. Change it to: *a real spend of app X is an action whose `rk = ak_X + [α]G` **and** whose nullifier equals `fvk_X`'s nullifier of a note in the signer's own scan of app X. This binding, not the key tweak, is what keeps one app's signing session from spending another app's notes.*
- The open decision "Review of the per-app key derivation, including Orchard's sign rule" now has a concrete spec, vectors, and the reviewer items in 5.2 and 5.5.
