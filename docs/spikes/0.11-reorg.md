# Spike 0.11: Zebra reorg behaviour, the deep-reorg limit and the zcashd claim

Date: 2026-10-10. Zebra 6.4.2 (`zfnd/zebra:6.4.2`, git `e3eef2f`) on regtest, with NU5 through NU6.3 active from height 1. The harness was `spikes/zebra/` (since removed; its scripts live on, for Zakura, in `infra/zakura/scripts/`); raw logs are in [`0.11-results/`](0.11-results/).

## Method

- Two Zebra nodes, `zol-zebra-a` and `zol-zebra-b`, each in its own container on the docker network `zol-zebra-p2p`.
- They peer through the regtest-only `addnode` RPC. Regtest refuses non-localhost initial peers (0.2).
- `scripts/reorg.sh B_LEN A_LEN [HOLD] [TIMEOUT]` runs one experiment:
  1. Mine a shared prefix and wait until both tips are equal.
  2. **Partition:** `docker network disconnect zol-zebra-p2p zol-zebra-b`. The container keeps running, and RPC goes through `docker exec`.
  3. Mine `B_LEN` blocks on b and `A_LEN` blocks on a, using `generate`.
  4. Hold the partition for 75 s, then check that b's tip has not moved. Every run: no leak.
  5. **Heal:** reconnect b and `addnode` both ways.
  6. Wait until b's tip equals a's tip. Then check that b's first fork block is off the best chain and that the block hash at base+1 matches a's.
- Regtest has no proof of work and a constant difficulty, so chain work equals length. On testnet and mainnet, cumulative work decides.

### The run beyond the window, in detail

Evidence from [`reorg-1005v1010-deep.log`](0.11-results/reorg-1005v1010-deep.log):
- b's sync loop restarts continually (`starting sync, obtaining new tips state_tip=Height(1063)`).
- One attempt logged `WARN … error downloading and verifying block e=ValidationRequestError { error: Elapsed(()), height: Height(101), hash: 021fb82b8bb2… }`. Block `021fb82b…` is **a's** block 101; b has `cb98008c…` at that height. b tried to fetch a's chain and gave up on a block whose parent it could never accept.
- `getblockchaininfo` on b reports `blocks: 1063` and **`verificationprogress: 1.0`**. The node looks healthy and synced.
- `invalidateblock` on b's first fork block (height 59, already finalized) fails with `block hash … not found in any non-finalized chain`. **The RPC cannot recover a node from this state.**

## Source analysis (Zebra 6.4.2)

**1. The constant is 1000, and it is a local policy.**
- [`zebra-chain/src/parameters/constants.rs` L20-30](https://github.com/ZcashFoundation/zebra/blob/e3eef2f37c35127ad1769f19a1ebc7eaa5d5d291/zebra-chain/src/parameters/constants.rs#L20-L30) defines `pub const MAX_BLOCK_REORG_HEIGHT: u32 = 1000;`. Its doc comment says: "This is a local-only node policy; it is not part of consensus."
- [`zebra-state/src/request.rs` L860-878](https://github.com/ZcashFoundation/zebra/blob/e3eef2f37c35127ad1769f19a1ebc7eaa5d5d291/zebra-state/src/request.rs#L860-L878) quotes the protocol spec, "For `zcashd` and `zebra` this limit is 100 blocks", and adds that Zebra's window "is now 1000 blocks, larger than the 100 quoted".

**2. How the window maps to the finalized state.**
- After every non-finalized commit, the write task finalizes the oldest best-chain block while `best_chain_len() > MAX_BLOCK_REORG_HEIGHT` ([`zebra-state/src/service/write.rs` L459-470](https://github.com/ZcashFoundation/zebra/blob/e3eef2f37c35127ad1769f19a1ebc7eaa5d5d291/zebra-state/src/service/write.rs#L459-L470)).
- Finalized blocks move into RocksDB, and side chains below them are discarded.
- So the finalized tip is always `tip − 1000`. A fork point below it is unreachable.

**3. Why a deeper reorg silently fails instead of halting.**
- **Commit path.** A block whose height is already in the finalized DB is answered as a *duplicate* (`KnownBlock::Finalized`) and dropped ([`zebra-state/src/service.rs` L749-760](https://github.com/ZcashFoundation/zebra/blob/e3eef2f37c35127ad1769f19a1ebc7eaa5d5d291/zebra-state/src/service.rs#L749-L760)). A block whose parent is not a valid fork point stays queued as "unready" (L817-818) and is pruned once the finalized height passes it (L823-831). The block-download timeout produces the `Elapsed` warning seen above.
- **Gossip path.** Gossiped blocks below the finalized tip are dropped: "gossiped block height behind the finalized tip: dropped downloaded block" (`zebrad/src/components/inbound/downloads.rs` around L500-512, `behind_tip_limit = MAX_BLOCK_REORG_HEIGHT`).
- **Block locators** reach back only `MAX_BLOCK_REORG_HEIGHT` below the tip (`zebra-state/src/service/read/find.rs` L278-300). A peer on a fork deeper than that finds no intersection and answers from genesis (L392-399). b already has those early blocks and cannot attach the later ones.
- **`invalidateblock` / `reconsiderblock`** only search non-finalized chains (`zebra-state/src/service/non_finalized_state.rs` L390-393).
- **Conclusion.** On a reorg deeper than the window, Zebra **neither halts nor refuses loudly. It stays on its own chain indefinitely**, keeps serving RPC as if synced, and needs **manual intervention**: stop it, delete the state or restore a trusted snapshot, then resync. Nothing in the code shuts the node down for this. My search found no `shutdown`, `panic` or alert tied to the reorg limit.

## The zcashd claim from the review

- **The review is right about the behaviour, if slightly off by one.**
  - In zcashd, `MAX_REORG_LENGTH = COINBASE_MATURITY - 1`, which is 99 ([`src/main.h` L62-64](https://github.com/zcash/zcash/blob/558f686599586f55def3db86955d74d3be44605e/src/main.h#L62-L64); `COINBASE_MATURITY = 100` in `src/consensus/consensus.h` L36).
  - In `ActivateBestChainStep` ([`src/main.cpp` L4718-4746](https://github.com/zcash/zcash/blob/558f686599586f55def3db86955d74d3be44605e/src/main.cpp#L4718-L4746)), a reorg with `reorgLength > MAX_REORG_LENGTH` logs "…would roll back %d blocks! This is larger than the maximum of %d blocks, and so the node is shutting down for your safety… Please help, human!" and calls `StartShutdown()`.
  - The same applies to rewinds (L7124-7140).
  - So zcashd shuts down on any reorg of **100 blocks or more**.
- **There is no `-maxreorgdepth` option.** I grepped `src/init.cpp` at the final commit: no reorg-depth option exists. The limit is a compile-time constant.
- **This no longer matters, because zcashd is end-of-life.**
  - The `zcash/zcash` repository is archived (last push 2026-07-19; final release v6.20.0, 2026-06-03).
  - Its README and `doc/book/src/user/end-of-life.md` say every zcashd 6.20.0 node hit its hard-coded End-of-Support halt (`DEPRECATION_HEIGHT`) on **2026-07-18 at height 3,417,100**, and will not restart.
  - zcashd does not support NU6.3, which activated about 10 days later. The network is Zebra-only; the README also names "Zakura", which I did not check.
  - Zebra's `zcashd-compat` sidecar mode runs a zcashd behind Zebra for wallet RPC. Zebra's tests show the sidecar shutting down at 99 blocks before `zebra-compat-v1.2.0`, and following deeper reorgs after it (`zebrad/tests/common/zcashd_compat/reorg.rs` L128-147). That sidecar does not support Ironwood, so it is irrelevant to ZOL.

## Conclusions

1. **Zebra reorgs automatically and correctly to the heavier chain at any depth up to about 999 blocks.** Measured at 3, 20, 150 and 995 deep. Equal-work forks do not switch; the first-seen chain is kept.
2. **Beyond 1000 blocks, Zebra silently forks off.** It does not halt, does not report an error, and reports `verificationprogress: 1.0`. Recovery is a manual wipe and resync.
   - If the honest network made the deep reorg, the node is now on a dead chain, and anything ZOL reads from it is wrong.
   - If the deep reorg is an attack, the node usefully refuses it, but just as silently.
3. **The review's zcashd fact is accurate (≥100 blocks leads to shutdown) but obsolete.** No zcashd node runs on mainnet after 2026-07-18.

## Implications for design-v0.3 (Confirmation policy, global halt)

- **Replace the zcashd sentence.** For example: "zcashd shut down on reorgs of 100 or more blocks, but has been end-of-life since 2026-07-18 and no longer runs. Zebra, now the only consensus node, keeps a 1,000-block window. Within it, Zebra reorgs automatically. Beyond it, Zebra stays on its own chain without halting or reporting an error."
- **The global halt has to be ZOL's own mechanism, because the node never halts.** Concrete triggers for 3.3:
  1. **Scanner-observed rollback.** The scanner stores `(height, hash)` for every block it has processed, and on each poll re-checks `getblockhash(h)` for the stored heights back to full depth plus a margin. A changed hash at depth ≥ full depth, or a paid transaction's block leaving the best chain (`getblock` returns `-5 "block height not in best chain"`), triggers the halt. Zebra emits no reorg event with a depth, so the scanner must detect reorgs itself.
  2. **Disagreement between nodes.** Operators exchange signed `(height, hash)` pairs at `tip − early depth` and `tip − full depth`. A mismatch triggers the halt. This is the only defence against a node silently forked by more than 1000 blocks, since `getblockchaininfo` looks normal.
  3. **Stalled node.** The local tip has not advanced within N times the expected block interval while the other operators' tips have, or repeated `error downloading and verifying block` warnings appear. Treat either as a halt.
  4. **Ideally two independent Zebra nodes per operator,** for example one from a snapshot and one synced from genesis, compared locally.
- **Keep every depth well inside the 1,000-block window.** Full depth and payout depth should be at most about 1/4 of it, so a rollback past them is still seen as a rollback rather than a silent split. Suggested starting values for 0.12:
  - early credit: about 10 blocks;
  - full depth: 100 blocks (about 2 h);
  - payout depth: 100 blocks.
  - The window is about 20.8 h at 75 s per block.
- **Restate depths for Ironwood/v6 only if the block interval changes.** NU6.3 did not change the 75 s target.
- **Write the halt and recovery runbook (6.3).**
  - A node off the honest chain: stop it, wipe the state, restore a trusted snapshot or resync, then compare its tip hashes with the other operators before restarting the gateway.
  - The design's "until operators intervene" is the only resolution. Zebra offers no automatic recovery.
- **Regtest coverage for 5.5.**
  - `scripts/reorg.sh` already reproduces depths from 1 to 999, ties, and splits beyond the window, in seconds: 2,000 blocks mine in about 4 s.
  - Shielded transactions still need to be added so that early-credit rollback and payout reorg can be tested end to end.
