# Spike 0.3: one-input vault payout through the real `pczt` roles

**Result: PASS** (offline). It was not broadcast: there is no funded testnet ZEC and no synced node. The broadcast step exists as a dry-run CLI.

## Recommendations

1. **Retarget the vault from the Orchard pool to the Ironwood pool.** The pinned `zcash_protocol` 0.10.6 defines NU6.3, which brings in the Ironwood value pool. Its activation heights are testnet 4,134,000 and mainnet 3,428,143. From NU6.3 on, consensus requires `enableCrossAddress = 0` for the Orchard pool, so an Orchard spend can only pay its own address. The spike confirms this: `add_orchard_output` to a foreign address fails with `CrossAddressDisabled`. A payout to a player is therefore only possible as a v6 transaction in the Ironwood pool, with V3 note plaintexts and a separate commitment tree and anchor. Both shapes pass end to end, so the code change is small. The design and plan text that says "Orchard pool" needs updating. I could not check the chain tip offline. By block-time arithmetic from NU6.1 (mainnet 3,146,400), mainnet NU6.3 activated around late July 2026, so it is very likely already active.
2. **Keep the pipeline as built:** `zcash_primitives` Builder, which drives `orchard::builder::Builder::build_for_pczt`, then `Creator::build_from_parts`, `IoFinalizer`, `Prover`, `Signer`, `SpendFinalizer` and `TxExtractor`. pczt 0.9.3 has no public way to put an `orchard::pczt::Bundle` into a PCZT made by `Creator::new()`. The `zcp-builder` feature's `Creator::build_from_parts` is the supported entry point, and it is what the pczt crate's own end-to-end tests use.
3. **For a v6 transaction with no transparent parts, the sighash equals the txid.** Both test transactions show this. Signers therefore know the payout txid before broadcast. Re-proving does not change it.
4. **In v6 the sighash no longer commits to the anchor.** ZIP 374 moves the anchor into the authorizing data. That is harmless for ZOL, but "the signature pins the anchor" is no longer true.

## What was tested

`spikes/zcash/tests/spike_0_3_pczt_payout.rs` runs these steps for both `Pool::OrchardNu62` (v5, Orchard, NU6.2) and `Pool::IronwoodNu63` (v6, Ironwood, NU6.3), using TEST_NETWORK parameters at heights 4,100,000 and 4,200,000:

1. **Single-key vault:** a random `SpendingKey`, giving an FVK and an `ask`.
2. **Head note:** a "deposit" bundle is built offline. It is unproven and pays 1,000,000 zat to the vault's external address. The vault IVK trial-decrypts it to get the `Note`.
3. **Own commitment tree** (`src/tree.rs`): 5 filler leaves, the head, then 3 more filler leaves. The root is computed layer by layer and cross-checked against `incrementalmerkletree::frontier::Frontier::root()`. The head's authentication path must root to the anchor.
4. **Payout:** one spend (the head) and two outputs:
   - 600,000 zat to an external address, using the vault external OVK and a memo.
   - The new head (change): 390,000 zat to the vault's internal address, using the vault internal OVK and a head memo.

   The fee is ZIP 317's 10,000 zat for 2 actions. The value balance equals the fee.
5. **Roles:** Creator, then IoFinalizer, Prover, `Signer::sign_orchard` or `sign_ironwood` (single key), SpendFinalizer and TxExtractor. TxExtractor itself batch-verifies the proof and the signatures.
6. **Independent verification** (`src/verify.rs`) starts from the raw bytes:
   - Parse with `Transaction::read` and check that it re-serializes identically.
   - Strip the authorization to effects only and recompute the ZIP 244 shielded sighash with `v5_signature_hash` or `v6_signature_hash`. It must equal the pczt Signer's sighash.
   - Verify every `spend_auth_sig` under its `rk`.
   - Verify `binding_sig` under `bvk`.
   - Run `Bundle::verify_proof` with a freshly built `VerifyingKey` for the pool's circuit version. Also run orchard's `BatchValidator`.
7. **Effects:**
   - The head nullifier is revealed.
   - The recipient's IVK decrypts exactly the payout, with the right value and memo.
   - The vault's IVKs (external and internal) decrypt exactly one output, the new head, with value 390,000 and the head memo.
   - The vault's two OVKs recover both outputs.
8. **NU6.3 Orchard-pool negative test:**
   - `add_orchard_output` to a foreign address returns `Err(OrchardRecipient(CrossAddressDisabled))`.
   - `add_orchard_change_output` to the vault's own address succeeds.

## The dummy spend: how it is carried and removed

There are 2 outputs and 1 real spend, which gives 2 actions. The builder pairs the payout and the head output with the real spend and with one dummy spend, then shuffles. The dummy is made by `SpendInfo::dummy` (`orchard` `builder.rs`): a fresh random `SpendingKey`, a zero-valued `Note::dummy` at that key's address, and a random Merkle path. The dummy's key is not under the anchor, but value 0 switches off the anchor check in the circuit.

| Stage | Dummy action's `spend.dummy_sk` | Dummy `spend_auth_sig` | `bsk` |
|---|---|---|---|
| After Creator | **present** (`SpendInfo.dummy_sk` → `pczt::orchard::Spend::dummy_sk`) | none | none |
| After IoFinalizer | **removed** (`action.spend.dummy_sk.take()` in `orchard/src/pczt/io_finalizer.rs`) | present, over the shielded sighash, verified by the spike under `rk` | set (Σrcv), and checked against Σcv_net − ValueCommit(value_sum, 0) |

IoFinalizer computes the sighash from the effects, signs every dummy spend with `SpendAuthorizingKey::from(&dummy_sk)`, and then drops the key. From then on the effects are frozen in practice: a later change breaks the dummy signatures, and TxExtractor fails with `SighashMismatch` (see spike 0.6). Field presence per action (Ironwood run; the Orchard run is identical):

```
| action | spend.value | recipient | rho | rseed | fvk | witness | alpha | dummy_sk | spend_auth_sig | output.value | out.recipient | out.rseed | ock | user_address | rcv |
after Creator
| 0 (dummy) | 0       | Y | Y | Y | Y | Y | Y | Y | - | 600000 | Y | Y | - | - | Y |
| 1 (real)  | 1000000 | Y | Y | Y | Y | Y | Y | - | - | 390000 | Y | Y | - | - | Y |
after IoFinalizer
| 0 (dummy) | 0       | Y | Y | Y | Y | Y | Y | - | Y | 600000 | Y | Y | - | - | Y |
| 1 (real)  | 1000000 | Y | Y | Y | Y | Y | Y | - | - | 390000 | Y | Y | - | - | Y |
```

The dummy spend keeps its own random FVK, witness, alpha and note plaintext. Only `dummy_sk` goes.

## Broadcast stub

`cargo run --bin broadcast -- <hexfile> zebra+http://HOST:PORT [--send]` first re-verifies the transaction offline. It then prints, or with `--send` sends, a JSON-RPC `sendrawtransaction`. With `lightwalletd://HOST:PORT` it prints a `grpcurl` `CompactTxStreamer/SendTransaction` command. It was only run in dry-run mode. These transactions would be rejected on a real network anyway, because their anchor is our private tree. A real run needs a funded note and an anchor from a synced Zebra.

## Implications for design v0.3

- Change "Orchard shielded pool" to the Ironwood pool after NU6.3, which means v6 transactions. The vault's FVK and addresses are unchanged, since Ironwood uses the same Orchard keys and raw receivers. Scanning, anchors and witnesses become per pool, and the genesis head must be an Ironwood note.
  - Any vault notes left in the Orchard pool can only be spent to self or migrated.
  - The plan's 0.3 testnet broadcast should target Ironwood.
- The roadmap prerequisite ("one-input payout with a dummy spend run through the real `pczt` pipeline") is met offline.
- "The coordinator signs the dummy spends itself before signers see the proposal" is exactly what IoFinalizer does. The coordinator must run IoFinalizer, then the Prover, and only then send the proposal to signers.
