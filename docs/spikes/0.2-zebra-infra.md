# Spike 0.2 (Zebra part): regtest infrastructure and the testnet operator setup

Date: 2026-10-10. Status: **regtest done and in use. Testnet is documented but has not been run**, because the disk budget rules out a sync.

## What was built

The regtest setup lives in `spikes/zebra/`:

| File | Purpose |
|---|---|
| `docker-compose.yml` | `zfnd/zebra:6.4.2` (zebrad v6.4.2, git `e3eef2f`, 2026-09-25; multi-arch, runs natively on arm64). Node `zebra-a` is always on. Node `zebra-b` is under the `pair` profile, for the reorg tests in 0.11. Both sit on the docker network `zol-zebra-p2p` |
| `regtest.toml` | The regtest config, mounted read-only |
| `scripts/up.sh [a\|pair]` | Start one node, or two nodes peered with each other |
| `scripts/mine.sh N [node]` | Mine N blocks with the `generate` RPC |
| `scripts/height.sh [node]` | Print the height and tip |
| `scripts/down.sh` | Stop everything. State is ephemeral, so nothing is left on disk |
| `scripts/peer.sh`, `scripts/partition.sh`, `scripts/reorg.sh` | Two-node partition and reorg harness (see 0.11) |
| `testnet.example.toml` | Operator config for testnet. Not run |

Ports:
- Node a's RPC is published on `127.0.0.1:${ZOL_ZEBRA_RPC_PORT:-18232}`.
- Node b's RPC is published on `127.0.0.1:${ZOL_ZEBRA_B_RPC_PORT:-18242}`.
- The scripts call RPC through `docker exec … curl`, so they keep working while a node is partitioned.
- Cookie auth is off on regtest only.

Usage:

```sh
cd spikes/zebra
./scripts/up.sh            # height=0
./scripts/mine.sh 10       # a height=10 tip=926d3a…  (0.76 s wall for 10 blocks)
./scripts/height.sh
./scripts/down.sh
```

## Key config facts (Zebra 6.4.2 source, checked)

**Network upgrades must be activated explicitly.**
- On Regtest, Zebra fills in only Overwinter through Canopy at height 1. NU5 and later stay inactive unless configured (`zebra-chain/src/parameters/network/testnet.rs` `for_regtest`, L385-425).
- `regtest.toml` sets `NU5 = NU6 = "NU6.1" = "NU6.2" = "NU6.3" = 1`.
- `getblockchaininfo` confirms that every upgrade through **NU6.3 (Ironwood, branch `37a5165b`)** is `active` from height 1: `consensus.chaintip = 37a5165b`.
- NU7 is not set.
- This matches mainnet, where NU6.3 activated at 3,428,143, and testnet, where it activated at 4,134,000 (ZIP 258).

**Ironwood consequences for later spikes on this chain.**
- Because NU6.3 is active, Orchard rules here are the post-Ironwood ones:
  - `valueBalanceOrchard ≥ 0` (`zebra-consensus/src/transaction/check.rs` L220-229).
  - Coinbase may not carry Orchard actions (L250-258).
  - Orchard actions may not transfer between addresses (ZIP 258).
- The `pczt` spikes 0.3-0.5 must therefore build **v6 / Ironwood** transactions. If a pre-Ironwood baseline is needed, a second config can omit `"NU6.3"`.
- Coinbase goes to a transparent address: the book's regtest `t27eWDgjFYJGVXmzrXeVjnb5J3uXDM9xH9v`. Regtest allows unshielded coinbase spends by default (`with_unshielded_coinbase_spends(…unwrap_or(true))`, testnet.rs L1044-1046), so test funds can be shielded from coinbase.

**Mining.**
- `generate N` (zebra-rpc `methods.rs` L3296-3360) builds a template, randomizes the coinbase data so forks don't collide, and calls `submitblock`.
- It only works where PoW is disabled, which is the case on Regtest.
- About 2,000 blocks took around 4 s on an M-series Mac.
- `generatetoaddress` is a stub that returns "not implemented" (L790-801).
- The `internal-miner` feature needs a custom build. It is not needed.

**Peering on Regtest.**
- Regtest only dials *localhost* initial peers (`zebra-network/src/config.rs` L266-271), so DNS names of other containers are filtered out.
- Cross-container peering uses the regtest-only `addnode <ip:port> add` RPC (`methods.rs` L3397-3424), which only supports `add`.
- Zebra treats 18233 as the Regtest P2P port and warns "invalid peer port" on zcashd's 18344, so the config uses 18233.
- First peering takes up to about 60 s, because the crawler interval is 61 s.

**Other useful RPCs present** (`methods.rs`): `invalidateblock` and `reconsiderblock`, but only for blocks in the non-finalized window; `getblockchaininfo`, `getpeerinfo`, `getrawtransaction`, `z_gettreestate`, `getblocktemplate`, `submitblock`.

## Testnet for operators (documented, not run)

**Config.** See `spikes/zebra/testnet.example.toml`:
- `network = "Testnet"`, P2P on 18233 (published), RPC on 18232 bound to localhost on the host.
- Cookie auth on; a persistent `cache_dir` volume.
- Checkpoint sync on, which is the default.
- Zebra also offers an experimental built-in light-client server and an `indexer_listen_addr`. These were not evaluated: the gateway scanner is expected to read blocks through JSON-RPC from its own node.

**Disk and sync.**

| | Testnet | Mainnet (for scale) |
|---|---|---|
| ZF snapshot, as of 2026-10-07 (testnet) / 2026-10-09 (mainnet) | Height 4,468,596; **11.3 GiB** zstd archive, made by zebrad 6.3.0, DB format v28 | Height 3,511,321; **254.4 GiB** |
| Disk to plan for | **About 30-40 GB at peak** (archive plus extracted state while unpacking), then the extracted state. This is my estimate: the manifest does not publish the extracted size. Leave headroom for growth | 300 GB per the book |
| Book's figure | About 10 GB (`book/src/user/requirements.md`). This is out of date: the snapshot archive alone is now 11 GiB | |

- Snapshot listing: `https://snapshots.zfnd.org/testnet/snapshots.json`.
- The book says unpacking "temporarily needs about twice" the archive size.
- **Recommended path:** download the latest testnet snapshot, check its `sha256`, extract it into `cache_dir` with `tar --zstd -xf <archive> -C <cache_dir>`, then start zebrad. It catches up the last few blocks in minutes.
- **Trust caveat:** the snapshot is trusted data from ZF, and its manifest is currently marked `"signing": {"status": "unsigned"}`. For signers, either sync from genesis or verify the snapshot tip against a second node.
- **Sync time:**
  - The book says only that a mainnet sync from genesis "takes days" and gives no testnet figure.
  - Testnet from genesis, with checkpoint verification up to the last checkpoint, is a guess of **several hours to about a day** on 4 cores and 16 GB of RAM. Not measured.
  - From a snapshot: download time for 11 GiB, plus minutes.
- **Hardware:** the book recommends 4 cores, 16 GB RAM and 300 GB disk for mainnet. Testnet needs much less disk. Plan for 2-4 cores and 8 GB of RAM.

**For ZOL signers.**
- Each signer and attestor runs its own Zebra, as the design requires.
- The global-halt check "signers' nodes disagree on the chain" needs each gateway to expose its node's `getbestblockhash` and `getblockhash(h)` at the confirmation depths to the other operators, for example signed with the operator key. Spike 0.11 shows why: a node that is off the honest chain still reports itself fully synced.

## Implications for design-v0.3

- **Pin the Zebra version: 6.4.2 now, and revisit at 7.0.0, which has an rc out since 2026-10-02.** The design said the version was open.
- **The design must be restated for NU6.3/Ironwood.** Every regtest test from now on runs post-Ironwood rules, which is what both mainnet and testnet now enforce. See 0.10, section 4.
- **The regtest harness is ready for Phase 3.2 (scanner) and Phase 5.5 (reorg suite).**
  - It still lacks a shielded funding helper (coinbase to transparent, then shield to Ironwood). That belongs with the 0.3 `pczt` work.
