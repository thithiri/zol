# Spike 0.9: MagicBlock ephemeral rollup for the pot

Date: 2026-10-10. The harness is in `spikes/magicblock/`. Raw results are in `spikes/magicblock/logs/*.jsonl`.

**Where it ran.** The devnet airdrop was refused for the whole session: `429 "You've either reached your airdrop limit today or the airdrop faucet has run dry"`, 20 tries over about 17 minutes. The program was therefore never deployed to devnet. The end-to-end runs used MagicBlock's local stack: `solana-test-validator` with the delegation program preloaded, plus `ephemeral-validator` 0.14.10. They were repeated with three delegation-program binaries:

- the one shipped in the npm package;
- **the devnet binary** (`solana program dump`, deployed 2026-10-06);
- the mainnet binary (deployed 2026-04-29).

Devnet facts that need no SOL were checked against the live devnet ERs: a zero-SOL fee payer, cloning, instruction support, and 72 real commit latencies. Those runs used simulation, a zero-fee transaction, and passive reads of history.

## Recommendations

1. **Remove the guessed grace-period race. Use the delegation program's own forced undelegation.**
   - At the session deadline, anyone calls a ledger instruction. It CPIs `RequestUndelegation` (DLP ix 26), signed by the pot PDA.
   - An honest validator returns the pot with its latest state within about 1 s (measured).
   - If the validator does not respond, after 9000 slots (about 60 min) the ledger CPIs `UndelegateWithRollbackAfterTimeout` (ix 27) and takes the pot back with its **last finalized base-layer state**.
   - The ledger only commits through `close_pot`, so no intermediate commits exist. The last finalized state is then the delegation-time state, meaning the frozen buy-ins.
   - `cash_out` then runs on whatever came back. `refund_pot` for delegated pots becomes unnecessary.
   - Caveats:
     - This exists on **devnet only** today. The mainnet delegation program rejects ix 26/27 as unknown.
     - ix 26 needs the **delegation rent payer** as a signer (see Integration notes).
2. **If `refund_pot` stays as designed, set the grace period to at least 9000 slots (about 60 min).**
   - The measured return is about 1 s locally. Devnet commits land 0–3 s after the rollup transaction (72 samples).
   - No MagicBlock bound exists below the DLP's own 9000-slot undelegation timeout. The validator retries pending settlement intents across restarts (v1.0.0 release notes).
   - A short grace, such as 2 minutes, would usually work but has no guarantee behind it.
3. **Pot return to payout: MagicBlock adds about 1–3 s plus Solana finalization (about 13 s on devnet or mainnet).**
   - There is no challenge window. The fraud-proof and challenge protocol is not live, and DLP `Finalize` accepts any commit from the delegation authority immediately.
   - The "plus MagicBlock's challenge window" term in Timing and costs should become 0.
   - This shifts the trust model: **the ER validator is trusted for pot results.** It can commit any sum-preserving seat vector. The ledger's frozen receipt and its `cash_out` checks are the only bounds. They already confine a fault to the pot's frozen players.
4. **Fees: the design's numbers match the current source and devnet, but not mainnet.**
   - Today's mainnet DLP charges one tenth of that.
   - On devnet the charge is capped at the delegation deposit, about 0.00295 SOL for a pot. In practice a pot session costs that deposit, whatever the number of commits.
5. **Session keys do not need SOL for rollup transactions.** The 10-commit limit does not affect pots: `close_pot` is a commit-and-undelegate, which is exempt.

## Measurements

Local stack, 11 full lifecycles: 6 with the npm DLP and 5 with the devnet DLP. Base slots are about 0.58 s with `--ticks-per-slot 64`. Every run returned the exact rollup state (`state_matches_er: true`), and `cash_out_check` passed after every return.

| Step | min | median | max |
|---|---|---|---|
| `delegate_pot` confirmed on base | 513 ms | 529 ms | 1546 ms |
| Delegated pot visible in ER (from delegate send) | 517 ms | 532 ms | 1555 ms |
| `move_seat` in ER, send→confirmed (n=55) | 1 ms | 2 ms | 53 ms (first tx) |
| `set_config` on base → new value seen by ER program | 399 ms | 528 ms | 1227 ms |
| `commit_pot` ER confirm | 3 ms | 4 ms | 48 ms |

| Commit → base copy at `finalized` | 16.3 s | 16.9 s | 39.7 s |
| `close_pot` ER confirm | 3 ms | 4 ms | 10 ms |
| **Return**: `close_pot` send → base owner is our program (confirmed) | **414 ms** | **518 ms** | **869 ms** |
| Return at `finalized` | 16.4 s | 16.8 s | 34.1 s |

- With `--ticks-per-slot 8` (64 ms slots), the return took 106 ms (confirmed) and 2.1 s (finalized). The latency is about 1–2 base slots plus finality.
- On base, `close_pot` is **one transaction**: DLP `CommitState` + `Finalize` + `Undelegate`, plus the callback into our program (`ProcessUndelegation`). There is no separate finalize step.

**Devnet, passive.** We scanned the last 5000 signatures on `MagicContext1111…` on each of `devnet-as`, `-eu` and `-us`. For every rollup transaction that scheduled a commit, we followed `ScheduledCommitSent` to its devnet base transaction (`logs/devnet-observe-*.jsonl`):

- 72 commits, all successful on base.
- Delay (base `blockTime` − ER `blockTime`, 1 s resolution): **median 1 s, max 3 s** (0 s: 29, 1 s: 36, 2 s: 2, 3 s: 5).
- No commit-and-undelegate fell in the sampled windows. Recent devnet `Undelegate` transactions in the DLP history all came from the TEE validator, whose RPC needs auth.
- The return transaction is the same single-transaction pipeline as a commit, so the commit delay is the best available proxy for return latency.

## Answers

### a. Can a keypair with no SOL be the fee payer for rollup transactions? **Yes**, on public ERs today

- **Local ER:** `nosol` (0 lamports on base and ER, the account does not exist) was the sole signer and fee payer for:
  - `move_seat` on a delegated pot, with and without preflight;
  - `commit_pot`, as the magic-program `payer`;
  - `close_pot`. The pot returned in 1.1–1.7 s.

  Its balance stayed 0 (`logs/experiments-*.jsonl`).
- **Devnet ER (`devnet-as`):** a transaction with fee payer `nosol` executed with `"err":null,"fee":0` (`logs/probe-devnet-er.jsonl`). It was a compute-budget-only transaction; no delegated account was available to write without SOL.
- **Docs:** "Normal ER transactions: 0 in the current release" ([fees and commit economics](https://docs.magicblock.gg/pages/ephemeral-rollups-ers/introduction/fees-and-commit-economics)). The pricing page lists a base fee of 0 on public nodes and 0.0000005 SOL on dedicated nodes. The validator has a `--basefee` flag.
- **Magic-program payer:** the `payer` is only charged when it is a delegated account with the magic fee vault (`charge_delegated_payer` in `programs/magic-program/src/utils/account_actions.rs`). Otherwise it is never debited.
- **Caveat:** a dedicated ER with a non-zero base fee would need a funded payer inside the rollup.

### b. How does a rollup program read a non-delegated account (`Config`, `App`)? **It is cloned read-only on demand and kept current by subscription**

- **Read:** `move_seat` takes `Config` (owned by our program on base, never delegated) as a read-only account. The first transaction that referenced it succeeded, so the ER fetched and cloned it on demand.
- **Ownership inside the ER:** the ER shows it owned by our program, with the base value.
- **Freshness:** after `set_config` on base, the ER program saw the new value 0.4–1.2 s after the base transaction was sent. That window includes about 0.5 s of base confirmation, so the ER lag is a few hundred ms (`config_update_visible_in_er_ms`).
- **Devnet:** an arbitrary base account read through `devnet-as` returned identical data in about 100–130 ms.
- **Writes fail:** writing it in the ER (`set_config` sent to the ER) fails with `InvalidWritableAccount`.
- **Mechanism:** Chainlink "fetches missing accounts, subscribes to remote changes" (`chainlink/README.md`). The provider keeps per-pubkey pubsub subscriptions and handles eviction (`chainlink/src/remote_account_provider/mod.rs`).
- **Staleness:** reads are eventually consistent, normally sub-second. If a subscription stalls, a read can be stale; v1.0.0 lists fixes for "silently stalled streams". The ledger must not rely on `Config`/`App` freshness inside the rollup for safety. For example, a freeze flag must be enforced at `delegate_pot` and `cash_out` on Solana, not in `move_seat`.

### c. Fraud-proof or challenge window before a commit is final? **None in production. Finality = Solana finality of one transaction**

- **DLP `Finalize`:** "Validate the new state (currently state is valid if committed from a whitelisted validator)" (`src/processor/fast/finalize.rs`).
- **DLP `CommitState`:** checks only that the signer equals `delegation_record.authority`, plus an optional per-program validator whitelist (`commit_state.rs`).
- **Observed:** commit, finalize and undelegate land in the same base transaction (local), and devnet commits land 0–3 s after the rollup transaction.
- **The fraud-proof design is not live:**
  - The validator v1.0.0 release notes (2026-10-06) say "Replica mode and the challenge protocol remains experimental in 1.0.0".
  - The docs say only "A dynamic fraud-proof mechanism enables fast state finalization" through a "decentralized Security Committee", with no period ([ER intro](https://docs.magicblock.gg/pages/ephemeral-rollups-ers/introduction/ephemeral-rollup)).
  - The design paper is arXiv 2502.10321 (Dynamic Fraud Proof).
- **Implication:** whatever the delegation authority commits is final once the transaction finalizes. The authority is the validator named at delegation, or MagicBlock's default.

### d. Forced undelegation and slashing: **forced undelegation exists on devnet only; no slashing**

**Mechanism** (delegation-program commit `ccd8e56`, 2026-07-08):

- `RequestUndelegation` (ix 26, `src/processor/fast/request_undelegation.rs`):
  - **Signers:** the delegated account, meaning the owner program via PDA seeds; and the **delegation rent payer**, which must equal `delegation_metadata.rent_payer`.
  - **Effect:** creates PDA `["undelegation-request", pot]` with `expires_at_slot = slot + 9000` (`DEFAULT_UNDELEGATION_REQUEST_TIMEOUT_SLOTS`, "9000 slots = 60min").
  - **Afterwards:** the validator can no longer make a plain commit (`OwnerRequestedUndelegation`), only a commit-and-undelegate.
- `UndelegateWithRollbackAfterTimeout` (ix 27):
  - **Access:** owner program only, and only after `expires_at_slot`.
  - **Effect:** releases the account to its owner with the **last finalized base-layer data**. It discards any pending (unfinalized) commit and refunds the record and metadata rent to the rent payer, with no fee charged.
  - **The caller must restore the data.** The DLP resizes the account to 0, so the owner program saves the data before the CPI and writes it back after. See `rollback_pot`.

**Experiments** (local stack running the devnet DLP binary, `logs/forced.jsonl`):

- **Honest validator (3 runs):**
  - After `request_pot_undelegation`, the ER on its own committed the latest rollup state and undelegated. The pot was owned by our program again **1.08–1.11 s** after the request transaction was sent.
  - The validator watches request PDAs (`ObservedUndelegationRequest`, `chainlink/src/chainlink/fetch_cloner/mod.rs`).
- **Dead validator:**
  1. Delegate, move, commit (state X), move again (state Y, uncommitted).
  2. `SIGSTOP` the ER.
  3. Rollback before any request: fails (`InvalidAccountOwner`). Rollback before timeout: fails (`UndelegationRequestNotExpired`, 0x33).
  4. After 9000 slots (610 s with fast slots), `rollback_pot` succeeded.
  5. Result: the owner is our program, the state is **X**, and `cash_out_check` passes.
  6. After `SIGCONT`, the ER still treated the pot as delegated and accepted rollup writes and a `close_pot`. The base pot was unaffected: the DLP no longer recognises the delegation.

**Deployment** (probed by simulation, `logs/probe-dlp.jsonl`):

|---|---|---|---|
| devnet (deployed 2026-10-06) | `MissingRequiredSignature` | `InvalidAccountOwner` | Yes: the handlers exist and fail only on the dummy accounts |
| mainnet (deployed 2026-04-29) | `InvalidInstructionData` | `InvalidInstructionData` | **No** |
| npm local dump | `InvalidInstructionData` | `InvalidInstructionData` | **No** |

**Slashing: none on-chain.**

- The DLP has no stake, bond or slash logic. Grep for slash, stake and challenge in `src/` and `dlp-api/` finds nothing.
- Validators are permissioned. A validator fees vault created by the admin acts as the whitelist (`init_validator_fees_vault.rs`).
- An owner program can restrict which validators may commit its accounts with `WhitelistValidatorForProgram`. The authority for that is "either the ADMIN_PUBKEY or the program upgrade authority".
- The DLP itself is upgradeable through a Squads multisig (README).
- Bonding and slashing appear only in the fraud-proof paper.
- **Ask MagicBlock:**
  - the mainnet date for ix 26/27;
  - whether 9000 slots is fixed;
  - whether a DLP admin can whitelist validators for our program without us.

### e. Fee model: **design numbers match the current source and devnet; mainnet is 10× lower; the charge is capped at the deposit**

- **How it is charged:** at undelegation the DLP charges `SESSION_FEE_LAMPORTS + COMMIT_FEE_LAMPORTS × (commits − 1)`. The count includes the final commit-and-undelegate. The charge is **capped at the lamports in the delegation record and metadata PDAs**, the deposit the rent payer locked at delegation. The rest is refunded (`process_delegation_cleanup`, `src/processor/fast/undelegate.rs`).
- **Constants:**
  - Since commit `cd12870` (2026-10-01, "Raise Delegation & Commit Fees 10x"): 3,000,000 and 1,000,000 lamports.
  - Before that: 300,000 and 100,000.
  - The deposit is funded at "legacy rent", (bytes + 128) × 6960, so it survives SIMD-0194.
- **Measured** with a dedicated rent payer (`e_fees` in `logs/experiments-*.jsonl`):

| DLP binary | Deposit locked | Charged after 0 / 1 / 3 extra commits |
|---|---|---|
| devnet (has `cd12870`) | 2,951,040 (record 1,559,040 + metadata 1,392,000) | **2,951,040 / 2,951,040 / 2,951,040**: the cap binds, the whole deposit is kept |
| mainnet (2026-04-29) | 2,951,040 | **300,000 / 400,000 / 600,000** |
| npm local dump | 2,951,040 | 300,000 / 400,000 / 600,000 |

- **10-commit limit, confirmed.** With a non-delegated payer, plain commits 1–10 succeed. Commit 11 fails with "sponsored commit limit exceeded … reached the limit of 10" (`COMMIT_LIMIT = 10`, `programs/magic-program/src/magic_sys.rs`). `close_pot` afterwards still works: commit-and-undelegate is exempt (`process_schedule_commit.rs`: limits are checked only `if !opts.request_undelegation`).
- **With a delegated fee payer and magic fee vault:** no limit, and a live fee of 100,000 lamports per account from commit 26. These fees are taken in the rollup from the delegated payer (docs; `charge_delegated_payer`).
- **Rollup transactions:** free (see a).
- The fees doc (verified 2026-08-20) already shows 3,000,000 / 1,000,000. The pricing page still shows 0.0003 / 0.0001.

### f. Owner while delegated; can the base program check the pot has returned? **Owner = DLP while delegated; yes, the owner check works**

- **While delegated:**
  - The base pot account is owned by `DELeGGvXpWV2fqJUhqcF5ZSYMS4JTLjteaAMARRSaeSh`.
  - Its data stays readable and holds the **last finalized commit**: the pre-delegation bytes until the first commit, then each commit's state.
  - `cash_out_check` logged `pot owner = DELeGG…` and failed with `NotReturned`.
- **After return:**
  - The owner is our program again, and the data equals the final rollup state.
  - `cash_out_check` passed (`returned; seats=4 sum=400`).
  - The account is re-created by our `process_undelegation` callback, injected by `#[ephemeral]`, discriminator `[196,28,41,206,48,37,51,167]` = `sha256("global:process_undelegation")[..8]`. The callback only works when the DLP's `undelegate-buffer` PDA signs.
- **Owner alone does not prove a return.** Because data is readable while delegated, `cash_out` must check the owner, never just deserialize. The design already does this.
- **After a rollback,** the owner is our program and the data is the last finalized commit.

Rules from the source:

- **Who may commit.** A commit is accepted only when the invoking program owns the account, the account signs, or the validator signs (`validate_commit_schedule_permissions`). Only the ledger's own rollup instructions can commit or return a pot.
- **Size limit.** An account larger than 10,240 bytes cannot be committed.
- **Untyped delegated accounts.** `del` accounts must be `UncheckedAccount` or `AccountInfo`. Anchor would re-serialize a typed account after it changed owner.
- **Serialize before committing.** A handler that mutates a typed account and then commits in the same instruction must call `account.exit(&crate::ID)?` before the commit CPI. The examples' `increment_and_commit` does this.

## Implications for design v0.3

| Section | Change |
|---|---|
| Pot / `refund_pot` | Use the forced-undelegation path in place of the timed refund for delegated pots (Recommendation 1). If the refund is kept, grace ≥ 9000 slots (about 60 min) and documented as "MagicBlock's own undelegation timeout", not a measured bound |
| Pot / `close_pot` | It must be the **only** commit path for a pot, with no `commit_pot`. Then a rollback returns exactly the frozen buy-ins. The 10-commit limit never applies |
| Sessions in MagicBlock, "the validator's option" | Forced undelegation removes the option to stall indefinitely, on devnet now and on mainnet once deployed. It does not remove validator trust: with no live fraud proofs, the delegation authority can commit any sum-preserving seat vector. Name the validator explicitly as a trusted party for pot outcomes in the Trust model, and pin the validator per pot (`DelegateConfig.validator`). Optionally use `WhitelistValidatorForProgram` (our upgrade authority or the MagicBlock admin can set it) |
| Rent payer for `delegate_pot` | The delegation `payer` becomes `rent_payer`. It must sign `RequestUndelegation`, gets the deposit back minus fees, and loses about 0.00295 SOL per session on current devnet. For permissionless forced return, make it a ledger-owned, system-owned PDA vault. **The SDK's `delegate_account` cannot do this**: it signs only with the pot and buffer seeds. The ledger needs its own copy of `delegate_account_inner` that adds the vault seeds to each `invoke_signed`. Otherwise the relayer key is the rent payer, and forced return depends on the relayer (liveness only) |
| Timing and costs | "Pot return to payout": MagicBlock adds about 1–3 s plus Solana finality (about 13 s). There is no challenge window. Fee row: "0.003 SOL per session + 0.001 per extra commit, capped at the delegation deposit (≈0.00295 SOL per pot), so ≈0.003 SOL per pot session; mainnet currently 0.0003 + 0.0001" |
| Signer rule 1 (Finalized) | "Plus any challenge period MagicBlock applies" → none today. Solana `finalized` on the `cash_out` slot is enough |
| `Config`/`App` in the rollup | Cloned read-only and subscription-updated (sub-second), but only eventually consistent. Enforce freeze and pause on Solana at `delegate_pot`/`cash_out`, not in `move_seat` |
| Session keys | Can be fee payers for rollup transactions with no SOL on public ERs. They still need someone to pay base-layer fees for `buy_in`/`leave_pot` |
| Open decisions | Close: fraud-proof window (none), commit→return bound (measured about 1 s, hard bound 9000 slots via request/rollback), zero-SOL session key (yes), undelegated reads (clone + subscription). Still open: mainnet rollout of ix 26/27 (ask MagicBlock); devnet end-to-end latency under load with our own program (blocked by faucet; one run with about 3 SOL closes it) |

Client account order for this macro-expanded struct (checked against the macro source and used by the spike client):

`payer, buffer_pot (["buffer", pot] under the LEDGER id), delegation_record_pot (["delegation", pot] under DLP), delegation_metadata_pot (["delegation-metadata", pot] under DLP), pot, validator, …your fields…, owner_program (= ledger id), delegation_program, system_program`

`remaining_accounts` follow.

Commit and undelegate from inside the rollup (`close_pot`):

    MagicIntentBundleBuilder::new(
        ctx.accounts.payer.to_account_info(),        // any signer; not charged unless delegated
        ctx.accounts.magic_context.to_account_info(),
        ctx.accounts.magic_program.to_account_info(),

    .commit_and_undelegate(&[ctx.accounts.pot.to_account_info()])

}

### Findings for the ledger author

- **No ledger bug found** on this path, including:
  - the three-level CPI depth on base (`forward` → ledger → DLP → system) and in the ER (`forward` → ledger → magic);
  - the untyped `del` pot, hand-serialized by `update_pot` before the delegate and commit CPIs;
  - `close_pot` setting `delegated = false` before `commit_and_undelegate`. The returned pot carries `delegated: false`, and `returned_amounts` accepts it.
- **Pass `validator` explicitly in `delegate_pot`.** `tests/src/lib.rs::delegate_ix` passes `validator: None`, which makes the DLP default to `MAS1Dt9q…` (Asia). On any other ER the pot would never appear: the local `mAGic…` identity, `devnet-eu`/`-us`, or TEE. The harness passes `Some(getIdentity of the ER)`.
- **Zero-SOL keys work as rollup payers, including as the `#[commit]` `payer`.** The `payer` in `ClosePot` is never charged unless it is a delegated account with the magic fee vault. A relayer does not need to fund session keys or app keys for rollup transactions.
- The coverage above does not include the refund and forced-undelegation paths. They are covered in LiteSVM (`tests/`) and, for the DLP side, in the spike above.

## Side effect on shared tooling

`cargo build-sbf --tools-version v1.52` installs platform-tools v1.52 in `~/.cache/solana/v1.52`. It also re-links the rustup `*-sbpf-solana-*` toolchain, and logged `uninstalling toolchain 1.84.1-sbpf-solana-v1.51`. A concurrent build pinned to v1.51 re-links on its next run. A build running at that exact moment could fail once.
